# 音视频通话来电接听场景实践

## 场景介绍

音视频通话类应用（如 IM、会议、客服）存在两类高频疑难：一是应用进程被系统预加载后收到后台来电，用户点击系统来电卡片的「接通」却一直卡在"接通中"；二是锁屏来电响铃并震动时按电源键静音，铃声停了但应用自管的震动却停不下来，出现"铃停震不停"。

本示例聚焦上述两类需要落地的疑难，基于 HarmonyOS 的[Call Service Kit（通话服务）](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/call-api)提供完整的实现与验证：

* **疑难一（预加载进程来电"卡接通中"）**：业务核心初始化全部收敛到 AbilityStage.onCreate，接听/拒接/挂断统一走系统的 voipCallUiEvent 事件订阅（订阅收敛在 AbilityStage，预加载进程同样生效），任何进程形态均可完整接听，从根因上消除"卡接通中"。
* **疑难二（锁屏电源键静音不停震）**：来电上报携带 isUserMuteRingToneAllowed: true，处理 VOIP_CALL_EVENT_MUTE_RINGTONE 静音事件，收到即停铃停震。

本示例全程本地模拟来电（不接推送服务、不接通话服务端），铃声、震动与来电触发均为本地实现，用于完整演示两条链路；方案核心（初始化收敛 + 系统来电卡片链路 + 电源键静音停震）可直接移植到真实的音视频通话业务。系统来电卡片、事件回调、接听机制均为真实系统行为（走系统通话服务，非模拟），模拟方式不影响最佳实践的正确性。

## 实现思路

1. 通话初始化收敛到 AbilityStage 音视频通话应用通常把通话初始化拆散在 AbilityStage 与 UIAbility 两处。当应用被杀后，系统可能按用户使用习惯自动预加载该应用：新进程只执行到 AbilityStage.onCreate，UIAbility 不会被创建。此时若通话初始化依赖 UIAbility 的阶段缺失，来电接听就只能走一半，一直卡在"接通中"。

   因此把通话初始化逻辑全部收敛到 AbilityStage.onCreate（阶段1），UIAbility 仅负责 UI 就绪与系统来电卡片拉起时的自动接听入口（阶段2），预加载进程同样具备完整接听能力。可在阶段1中通过 application.getAppPreloadType() 识别当前进程的预加载类型（详见[应用预加载](https://device.harmonyos.com/cn/docs/apiref/harmonyos-guides/preload-application)），用于差异化初始化。

   ```ts
   // MyAbilityStage.ets
   import { AbilityStage } from '@kit.AbilityKit';
   import { CallCenter } from '../call/CallCenter';

   export default class MyAbilityStage extends AbilityStage {
     onCreate(): void {
       // 通话初始化 + voipCallUiEvent 订阅 + coreReady=true; 预加载进程也只执行到这里
       CallCenter.initStage1(this.context);
     }

     onDestroy(): void {
     }
   }
   ```

   ```ts
   // CallCenter.ets
   static initStage1(context: common.Context): void {
     CallCenter.appContext = context;
     CallCenter.applicationContext = context.getApplicationContext();
     CallCenter.bundleName = context.applicationInfo.name;
   // 接听/拒接/挂断全部走 voipCallUiEvent 与系统来电卡片; 订阅收敛在本初始化链路
     CallCenter.subscribeVoipCallEvents();
     CallCenter.callReady = true;
     CallStateStore.init(context, process.pid, CallCenter.getPreloadTypeValue());
   }
   ```

2. **来电上报 voipCall（开启静音停震能力）**

   来电到达时刻调用 voipCall.reportIncomingCall 向系统上报来电。上报时有两处关键设置：
   * isUserMuteRingToneAllowed: true 是电源键静音事件的开关，为 true 时系统才会在电源键静音时下发 VOIP_CALL_EVENT_MUTE_RINGTONE 事件，应用自管的铃声/震动才有停止入口；
   * userProfile 为来电头像 PixelMap，按 32vp × densityPixels 缩放输出，避免图片超限导致卡片头像区空白。

   示例中来电上报与状态置 RINGING、震动启动置于同一时机点"来电到达时刻"，保证链路一致。

   ```ts
   // CallCenter.ets
   private static reportVoipIncomingCall(): void {
     const callId: string = 'harmocallanswer_' + Date.now();
     CallCenter.currentCallId = callId;
     CallCenter.buildUserProfilePixelMap().then((pixelMap: image.PixelMap | null) => {
       if (pixelMap === null) {
        // 来电头像解码失败, 跳过 voipCall 上报并停铃停震, 不中断流程
         CallCenter.stopRingAndVibrate();
         return;
       }
       const attribute: voipCall.VoipCallAttribute = {
         callId: callId,
         voipCallType: voipCall.VoipCallType.VOIP_CALL_VOICE,
         userName: '模拟来电',
         userProfile: pixelMap,         // 必填: 真实头像 PixelMap, 空图会致卡片头像区空白
         abilityName: 'EntryAbility',   // 必填: 系统来电卡片「接听」拉起的就是它
         voipCallState: voipCall.VoipCallState.VOIP_CALL_STATE_RINGING,// 必填: 初始来电态
         showBannerForIncomingCall: true, // 仅影响横幅形态, 不阻止系统来电卡片,false时亮屏桌面来电收敛为灵动胶囊、不弹系统来电卡片（锁屏/通知中心仍显示）;true亮屏也弹完整卡片;本工程采用true
         isUserMuteRingToneAllowed: true   // 核心字段: true 才下发电源键静音事件
       };
       voipCall.reportIncomingCall(attribute).then((reason: voipCall.ErrorReason) => {
         if (reason === voipCall.ErrorReason.ERROR_NONE) {
        // 上报成功, 系统来电卡片弹出
         }
       });
     });
   }
   ```

3. **电源键静音事件处理（停铃停震）**

   订阅 voipCallUiEvent 事件，收到 VOIP_CALL_EVENT_MUTE_RINGTONE 时停止铃声与震动。事件订阅收敛在 AbilityStage 初始化链路，因此无论进程是否被预加载都会生效。

   处理时先按 callId 匹配当前通话，避免误停其它会话的资源；静止时不依赖自记录的资源状态，统一调用停止接口，保证"铃停震停"的即时性与收敛性。

   ```ts
   // CallCenter.ets
   private static subscribeVoipCallEvents(): void {
     try {
       voipCall.on('voipCallUiEvent', (info: voipCall.VoipCallUiEventInfo) => {
         CallCenter.onVoipCallUiEvent(info);
       });
     } catch (error) {
       // 订阅失败处理
     }
   }

   private static onVoipCallUiEvent(info: voipCall.VoipCallUiEventInfo): void {
     // 事件 callId 与当前通话不匹配时忽略
     if (info.callId !== CallCenter.currentCallId) {
       return;
     }
     switch (info.voipCallUiEvent) {
       case voipCall.VoipCallUiEvent.VOIP_CALL_EVENT_MUTE_RINGTONE: // 电源键静音
         RingPlayer.stop();     // 停铃声
         VibrateManager.stop(); // 停震动(清续播定时器 + stopVibration 停全部)
         break;
       case voipCall.VoipCallUiEvent.VOIP_CALL_EVENT_VOICE_ANSWER:  // 语音接听
         if (CallCenter.callState === CallState.RINGING) {
           CallCenter.handleAnswer();
         } else {
         // 已流转, 忽略
         }
         break;
       case voipCall.VoipCallUiEvent.VOIP_CALL_EVENT_REJECT:    // 拒接
       case voipCall.VoipCallUiEvent.VOIP_CALL_EVENT_HANGUP:      // 挂断
         if (CallCenter.callState === CallState.RINGING ||
           CallCenter.callState === CallState.CONNECTING ||
           CallCenter.callState === CallState.CONNECTED) {
           CallCenter.handleReject();
         } else {
        // 已流转, 忽略
         }
         break;
       default:
         break;
     }
   }
   ```

4. **系统来电卡片拉起自动接听 + 两次状态上报**

   系统来电卡片两个按钮的行为不同（Call Service Kit 机制）：
   * **拒接**：系统直接下发 REJECT 回调（voipCallUiEvent），应用收到后走完整终态链路（停铃停震、上报 DISCONNECTED，卡片消失）；
   * **接听**：系统直接拉起 abilityName 指定的 Ability，由其启动入口自行完成接听------首次通话不下发 VOICE_ANSWER 回调。因此 EntryAbility 的 onCreate（预加载/被杀进程路径）与 onNewWant（进程存活路径）需检测 RINGING 并调用 answerFromSystemCard 自动接听。

   接听后采用官方推荐的「两次状态上报」：收到接听后立即上报 ANSWERED（卡片即时反馈"正在接通"），接通成功后上报 ACTIVE（卡片显示"通话中"）；拒接/超时/挂断上报 DISCONNECTED（卡片消失）。

   ```ts
   // EntryAbility.ets
   private handleIncomingCallLaunch(want: Want, source: string): void {
     // want.parameters 打日志用于观察系统拉起是否携带 callId 等可判别字段
     if (CallCenter.getCallState() === CallState.RINGING) {
       CallCenter.answerFromSystemCard();// RINGING 守卫; handleAnswer 内部另有幂等保护
     }
   }
   ```

   ```ts
   // CallCenter.ets
   private static handleAnswer(): void {
     if (CallCenter.callState === CallState.CONNECTED ||
       CallCenter.callState === CallState.CONNECTING) {
       return; // 已处于接通中/通话中, 忽略本次接通
     }
     CallCenter.clearNoAnswerTimer();
     RingPlayer.stop();
     VibrateManager.stop();
     CallCenter.callState = CallState.CONNECTING;
     CallStateStore.saveCallState(CallState.CONNECTING);
     // 两次状态上报: 收到接听后立即上报 ANSWERED, 卡片即时反馈"正在接通"
     CallCenter.reportVoipCallState(voipCall.VoipCallState.VOIP_CALL_STATE_ANSWERED);
     setTimeout(() => {
       CallCenter.finishConnecting();
     }, CallCenter.CONNECT_TIMEOUT_MS);
   }

   private static finishConnecting(): void {
     if (CallCenter.callState !== CallState.CONNECTING) {
       return;
     }
     CallCenter.callState = CallState.CONNECTED;
     CallStateStore.saveCallState(CallState.CONNECTED);
   // 接通成功上报 ACTIVE, 系统卡片自行显示"通话中"
     CallCenter.reportVoipCallState(voipCall.VoipCallState.VOIP_CALL_STATE_ACTIVE);
   }
   ```

5. **状态闭环与资源清理**

   完整的通话必须完成状态闭环上报：来电建立失败时调用 reportIncomingCallError 通知系统（避免占用系统侧导致第二次来电返回 VOIP_CALL_EXISTS，值为 2），拒接/超时/挂断时报 DISCONNECTED 且清理 callId 会话。

   示例同时管理两类"模拟"资源：铃声（AVPlayer 自播合成音，因后台自播需申请音频长时任务 + AVSession 保活）与震动（vibrator 循环续播，可即时停止）。这两类资源在真实业务中通常由系统通话服务或通话 SDK 承担，示例中仅用于复现"应用自管资源被卡住"的问题形态。

   ```ts
   // CallCenter.ets ------ 终态统一走 handleReject(): 停铃停震停长时任务 + 上报 DISCONNECTED + 清理 callId
   private static handleReject(): void {
     if (CallCenter.callState === CallState.IDLE ||
       CallCenter.callState === CallState.REJECTED ||
       CallCenter.callState === CallState.ENDED) {
       return;
     }
     CallCenter.clearNoAnswerTimer();
     RingPlayer.stop();
     VibrateManager.stop();
     BackgroundAudioTask.stop();
     const endState: CallState =
       CallCenter.callState === CallState.RINGING ? CallState.REJECTED : CallState.ENDED;
     CallCenter.callState = endState;
     CallStateStore.saveCallState(endState);
    // 拒接/超时/挂断上报 DISCONNECTED, 系统来电卡片自行消失
     CallCenter.reportVoipCallState(voipCall.VoipCallState.VOIP_CALL_STATE_DISCONNECTED);
     CallCenter.currentCallId = ''; // 会话结束, 清理 callId
   }
   ```

   ```ts
   // VibrateManager.ets ------ 震动可即时停止: 清续播定时器 + stopVibration 停全部
   static stop(): void {
     if (!VibrateManager.isVibrating) {
       return;
     }
     VibrateManager.isVibrating = false;
     VibrateManager.cancelSchedule();
     vibrator.stopVibration().then(() => {
      // 来电震动已停止
     }).catch((error: BusinessError) => {
      // 停止震动失败处理
     });
   }
   ```

## 约束与限制

* 本示例支持 API Version 23 Release 及以上版本（isUserMuteRingToneAllowed 与 VOIP_CALL_EVENT_MUTE_RINGTONE 起始版本为 API Version 22）。
* 本示例基于 HarmonyOS 6.1.0(23) 真机验证，需使用 HarmonyOS 6.1.0 Release SDK 及以上版本。
* 本示例需要使用 DevEco Studio 6.x Release 及以上版本进行编译运行。
* 本示例仅支持手机形态（deviceTypes 配置为 phone）。
* 预加载由系统按用户使用习惯决定，应用不可控，存在概率性。
* 进程被杀后系统来电卡片「接听」不会自动接通（新进程内存态为 IDLE、无 callId）；真实业务可依据系统拉起 want.parameters 携带的 VoIPCallId 恢复会话接听，本示例记为已知限制、未实现恢复逻辑。

## 常见FAQ

Q：为什么初始化一定要放在 AbilityStage，不能放在 UIAbility？

A：预加载进程只执行到 AbilityStage.onCreate，UIAbility 不会创建。初始化依赖 UIAbility，预加载进程就"只走了一半"，接听必然失败，这是"卡接通中"的根因。

Q：为什么必须上报 isUserMuteRingToneAllowed？

A：它是电源键静音事件的开关：为 true 时系统才会在电源键静音时下发 VOIP_CALL_EVENT_MUTE_RINGTONE 事件，应用才能停掉自管的铃声/震动；不报或为 false 时事件不下发，自管资源失去停止入口，这正是"铃停震不停"的根因。

Q：真实业务中震动由谁管？

A：取决于业务实现：若震动由系统通话服务/通话 SDK 承担，电源键静音时系统一并处理，应用无需关心；若应用自管震动，必须上报 isUserMuteRingToneAllowed 并用 MUTE_RINGTONE 事件停止。同理，系统播放铃声时系统会静音铃声流（铃声停），应用自管部分仍靠事件停止（震动停）。

Q：系统来电卡片点「接听」为什么不走回调而是拉起应用？

A：这是系统来电卡片的设计：拒接 = 系统直接下发 REJECT 回调；接听 = 系统直接拉起 abilityName 指定的 Ability、由其启动入口自行完成接听（首次通话不下发 VOICE_ANSWER 回调）。因此 EntryAbility 的 onCreate/onNewWant 需检测 RINGING 并自动接听，并采用两次状态上报（ANSWERED → ACTIVE）让卡片即时反馈。

Q：进程被杀后点系统卡片「接通」会怎样？

A：不接通------新进程启动后内存态为 IDLE、无 callId，RINGING 判据不命中。真实业务可依据系统拉起 want.parameters 携带的 VoIPCallId（真机实测与上报 callId 一致）恢复会话接听；本示例记为已知限制、未实现恢复逻辑。
