# Camera (Beta)

#### Scenario

HiCar can discover the in-vehicle cameras, including the factory-installed and user-installed cameras. Leveraging the capabilities of these cameras, HiCar can provide more value-added services for users. Examples:

     * **In-vehicle video call/conference call** : Users can use their in-vehicle camera and large screen to make a video call/conference call while ensuring driving safety (for example, in parking mode).
     * **Driver monitoring** : The AI computing power of HUAWEI HiCar phones and real-time data reported by driver seat cameras can be used to monitor drivers in real time and intelligently alert drivers when necessary.
     * **Gesture recognition** : The AI computing power of Huawei HiCar phones and real-time data reported by driver seat cameras can be used to recognize drivers' gestures to control HiCar apps and services.
     * **Driving safety assistance** : The AI computing power of Huawei HiCar phones and real-time data reported by dashcams can be used to perform auxiliary detection on driving safety and intelligently alert users.

There are two types of cameras in the head unit:

     * Android camera: Cameras that can be used through standard Android APIs. If the HiCar SDK needs to use Android Camera, call **setAndroidCamInfos** by referring to [Configuring Camera Information](https://developer.huawei.com/consumer/cn/doc/development/SmartTravel-Guides/configure-camera-0000001064941294) to report the corresponding camera information during the initialization of the HiCar SDK.
     * Native camera: Cameras that cannot be used through the standard Android APIs. If the HiCar SDK needs to use the native camera, perform adaptation based on the camera-related APIs provided by HiCar in advance by following instructions in this section. After the adaptation is complete, call **setNativeCamInfos** to report the corresponding camera information during the initialization of the HiCar SDK. For details, please refer to [Configuring Camera Information](https://developer.huawei.com/consumer/cn/doc/development/SmartTravel-Guides/configure-camera-0000001064941294).

#### Interaction Process

     1. After the DMSDP Device service starts on the head unit, the DMSDP process searches for the **libdmsdpcamerahandler.so** file in the specified directory (**/system/lib** or **/system/lib64** depending on the operating system version) and dynamically loads the file.
     2. The HMI app calls **DMSDPGetCameraHandler** to obtain the handle and pointer set of the functions in the .so file. The obtained handles and pointers will be used for subsequent service operations.
     3. The HMI app registers a service status listener with the head unit. In the actual implementation, the listener pointer is cached for reporting the camera status changes (for example, busy or idle) or quantity changes (for example, a USB camera is inserted or removed).
     4. The HMI app calls **GetCameraCapability** to query the camera capabilities of the head unit, including the number of cameras, ID of each camera, supported resolution, frame rate, and data format. If the head unit has multiple cameras, it needs to determine which cameras are used for distributed virtualization based on the actual service requirements. While a camera may have multiple capabilities, only one capability supported by the DMSDP needs to be reported. It is recommended that the H.264 or H.265 data type be returned. If the camera does not support the output of H.264/H.265 video streams, the NV21 or RGB565 format is also acceptable.
     5. The head unit returns the camera capability information.
     6. In the implementation of the camera APIs, the head unit needs to monitor the camera status reported locally. For example, the head unit needs to perform the following: (1) Detects that the camera is busy when it is enabled. (2) Queries the camera information when a USB camera that will be used for distributed virtualization is inserted. (3) Detects loss of a reported USB camera when it is removed.
     7. The head unit needs to send the camera status changes detected in step 6 to the DMSDP Device SDK through the service listener registered in step 3.
     8. After receiving the camera status changes, the DMSDP Device SDK updates the local cache information and reports the changes to the phone.
     9. Before the head unit opens the camera, the DMSDP Device SDK calls **RegisterSendDataCallback** to register the handle of the data callback function and uses the handle to send back camera video stream data.
     10. The DMSDP Device SDK calls **OpenCamera** to open the camera. The API carries the camera parameters.
     11. The HMI app calls the camera-related APIs of the head unit to open the head unit camera.
     12. After the camera is launched, the camera data is returned.
     13. The handle of the data callback function registered in step 9 is used to send back the collected data.
     14. During service running, the camera configuration, such as the camera frame rate, may be updated. In this case, the **UpdateConfig** API needs to be called to deliver the new configuration.
     15. The HMI app calls the corresponding API of the head unit to update the configuration. If configuration updating is not supported, the API implementation can be blank.
     16. The head unit returns the configuration update result.
     17. The configuration update result is returned.
     18. The DMSDP Device SDK calls the **CloseCamera** API to close the camera.
     19. The API that closes the camera of the head unit is called.
     20. The locally cached resources are released, such as the handle of the data callback function.
     21. The camera is closed successfully.

The DMSDP Device SDK is an internal service module of the HiCar SDK. It implements distributed virtualization of head unit peripherals and directly calls the **libdmsdpcamerahandler.so** file.

#### Development Procedure

Implement the camera-related APIs based on the camera API header files described in this section, and build the dynamic-link library file (.so) for the HiCar SDK to call.

The defined camera APIs abstract camera operations and encapsulate them into APIs for enabling, disabling, updating settings, querying capabilities, registering event listeners, and more. Implement the basic camera operations based on the API descriptions.

The aforementioned header files are listed as follows:
    
    **dmsdp_business.h** : defines result codes and status codes.
    **dmsdp_camera_data_type.h** : defines the camera data objects.
    **dmsdp_camera_handler.h** : defines the camera APIs.

     1. Sort out the camera hardware information of the head unit and determine the head unit cameras that need to be virtualized in distributed mode for the phone. Only the cameras that will be used in virtualization need to have their information collected and reported.
     2. The DMSDP Device SDK needs to operate the camera of the head unit through the corresponding APIs. The implementation must include a mechanism to resolve possible conflicts between the SDK and other in-vehicle services in using the camera.
     3. If the head unit has the camera status changed after it reports the camera information to the phone, and the changes involve the camera used in virtualization services, the head unit must monitor the changes.
     4. Implement the camera-related APIs based on the camera API header files, and provide the camera operating and status listening capabilities.
     5. Use the preceding header files to generate the **libdmsdpcamerahandler.so** file, and generate a 32-bit or 64-bit dynamic library depending on the operating system version. The dynamic library file needs to be stored in the **/system/lib** or **system/lib64** directory based on the service requirements.

When running, the HiCar SDK searches for the .so file in the preceding directory. If the file is not found, it is considered that the camera-related APIs have not been implemented. If the file is found, the SDK dynamically loads the dynamic-link library and obtains camera data from the head unit through the APIs implemented in the library.
