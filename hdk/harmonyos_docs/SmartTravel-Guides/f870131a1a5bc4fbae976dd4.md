# Bluetooth

#### Configuring BLE Advertising Settings

As HiCar uses BLE advertising for service discovery, the head unit must contain its Classic Bluetooth (BR) address, instead of a random MAC address, in its BLE advertising packets. This allows the Huawei HiCar phone to use this address to perform Bluetooth pairing and establishing a BR link during the connection process.

To configure BLE advertising packets to contain the Classic Bluetooth (BR) address, use either of the following methods:

The following uses the Android 8 system as an example. Make adaptation to the actual conditions. For details about the adaptation and modification solutions for other versions, please refer to [Precautions for Android 10.0 Adaptation](https://developer.huawei.com/consumer/cn/doc/development/SmartTravel-Guides/android-10-adaptation-0000001050028055) or [Precautions for Android 9.0 Adaptation](https://developer.huawei.com/consumer/cn/doc/development/SmartTravel-Guides/android-9-adaptation-0000000000044614).

#### [h2]Method 1: Modifying the Configuration File

     1. Search for **system\bt\include\bt_target.h** in the Android source code and change the value of **BLE_LOCAL_PRIVACY_ENABLED** to **FALSE** as follows:
            
            /*
             * Enables or disables support for local privacy (ex. address rotation)
             */
            #ifndef BLE_LOCAL_PRIVACY_ENABLED
            #define BLE_LOCAL_PRIVACY_ENABLED **FALSE**    //Change the flag to FALSE.
            #endif

     2. Search for **frameworks\base\core\res\res\values\config.xml** in the Android source code and change the value of **config_bluetooth_le_peripheral_mode_supported** to **true** as follows:
            
            <!-- Boolean indicating if current platform supports BLE peripheral mode -->
            <bool name="config_bluetooth_le_peripheral_mode_supported">**true** </bool>    //Set the value to true.

#### [h2]Method 2: Modifying the Protocol Stack

     1. Search for **system\bt\stack\btm\btm_ble_addr.cc** in the Android source code.
     2. Make the following changes for the **btm_gen_resolve_paddr_cmpl** function:
            
            static void btm_gen_resolve_paddr_cmpl(tSMP_ENC* p) {
              tBTM_LE_RANDOM_CB* p_cb = &btm_cb.ble_ctr_cb.addr_mgnt_cb;
              BTM_TRACE_EVENT("btm_gen_resolve_paddr_cmpl");
              if (p) {
                /* set hash to be LSB of rpAddress */
                p_cb->private_addr[5] = p->param_buf[0];
                p_cb->private_addr[4] = p->param_buf[1];
                p_cb->private_addr[3] = p->param_buf[2];
                /* set it to controller */
            
                //Change 1:
                **if(btm_ble_set_random_address(*controller_get_interface()- >get_address())){ **
            **p_cb- >last_private_addr=*controller_get_interface()->get_address(); **
            **}else{**
            **p_cb- >private_addr=*controller_get_interface()->get_address(); **
            **}**
            
                //Change 2:
                p_cb->own_addr_type=**BLE_ADDR_PUBLIC** ; //The original value is **BLE_ADDR_RANDOM**.
            
                /* start a periodical timer to refresh random addr */
                period_ms_t interval_ms = BTM_BLE_PRIVATE_ADDR_INT_MS;
            #if (BTM_BLE_CONFORMANCE_TESTING == TRUE)
                interval_ms = btm_cb.ble_ctr_cb.rpa_tout * 1000;
            #endif
                alarm_set_on_queue(p_cb->refresh_raddr_timer, interval_ms,
                                   btm_ble_refresh_raddr_timer_timeout, NULL,
                                   btu_general_alarm_queue);
              } else {
                /* random address set failure */
                BTM_TRACE_DEBUG("set random address failed");
              }
            }

The following describes the two changes:

        1. For **btm_ble_set_random_address(*controller_get_interface()- >get_address())**, change the original code to the snippet above.
        2. For **p_cb- >own_addr_type=BLE_ADDR_PUBLIC**, change the value from **BLE_ADDR_RANDOM** to **BLE_ADDR_PUBLIC**.
     3. (Optional) Handle possible alarms.

Change 1 may generate an alarm in some editors. In this case, clear the alarm with the following snippet:
            
            p_cb->own_addr_type=BLE_ADDR_PUBLIC; //BLE_ADDR_RANDOM
            **p_cb- >private_addr=*controller_get_interface()->get_address();**
            **btm_ble_set_random_address(p_cb- >private_addr); **

#### Handling Bluetooth Conflicts

#### [h2]Processing Bluetooth Mutual Conflicting

Assuming that the head unit supports only one-to-one Bluetooth pairing with a mobile phone and mobile phone A has been paired with the head unit via Bluetooth. When mobile phone B responds to the HiCar wireless connection, the RFCOMM connection initiated by mobile phone B to the head unit will be rejected or cannot be connected due to other reasons.

During HiCar SDK advertising, if the head unit detects that another mobile phone initiates an RFCOMM connection, it is recommended that the head unit proactively disconnect the Bluetooth connection of the previous mobile phone after the Bluetooth ACL connection is established between the other mobile phone and the head unit. The following are two solutions:

     * (Recommended) Complete the preceding logic processing in the Bluetooth protocol stack.
     * Complete the preceding logic processing in the vendor's HMI app.

#### [h2]Handling the Conflict Between the HFP and HiCar Calls

During a HiCar call, the Bluetooth SCO link connection is triggered. As a result, the Bluetooth call on the head unit side applies for the call focus and executes incoming call services, and there may be no sound during the HiCar call. The possible solutions to the conflict between the HFP and HiCar are as follows:

     * (Recommended) Turn off the HFP when the HiCar is in the connected state.
       1. Disable the HFP when the HiCar is in the connected state. (A possible solution is to disable the HFP through the non-standard interface of the protocol stack, or disconnect the HFP when the HFP connection is successful and the HiCar is connected.)
       2. After the HFP is disconnected, the Bluetooth calling feature is unavailable on the head unit. When a user uses the Bluetooth calling app on the head unit, a message is displayed, for example, "HUAWEI HiCar is connected. Bluetooth calling is temporarily unavailable. Please use the HUAWEI HiCar calling app."
     * When a HiCar call is initiated, the Bluetooth SCO link connection is blocked. The connection is resumed after the call is put through.
     * Disable Bluetooth when the HiCar is in the connected state.

#### [h2]Handling the Conflict Between A2DP and HiCar Music

HiCar music playback may conflict with A2DP. As a result, the local Bluetooth music playback/pause features do not work. The possible solutions to the conflict between the A2DP and HiCar music playback are as follows:

     * (Recommended) Turn off the A2DP when the HiCar is in the connected state.
       1. Disable the A2DP when the HiCar is in the connected state. (A possible solution is to disable the A2DP through the non-standard interface of the protocol stack, or disconnect the A2DP when the A2DP connection is successful and the HiCar is connected.)
       2. After the A2DP is disconnected, Bluetooth music is unavailable on the head unit. When a user uses the Bluetooth music app on the head unit, a message is displayed, for example, "HUAWEI HiCar is connected. Bluetooth music is temporarily unavailable. Please use the HUAWEI HiCar music app."
     * Reconstruct the Bluetooth music software on the head unit side when the HiCar is in the connected state. Convert the related control commands into HiCar key events and report the commands to the HiCar through the APIs provided by the HiCar SDK.
     * Disable Bluetooth when the HiCar is in the connected state.

#### [h2]Notes

If the solution of disconnecting the HFP or A2DP is used, after the HiCar is disconnected, an automatic HiCar connection may be triggered again due to the reconnection between the Bluetooth HFP and A2DP. It is recommended that the HiCar does not respond to the automatic connection within a fixed period of time after it is disconnected. (The timeout period for HFP reconnection can be used as a reference. The recommended period is around 30s.)
