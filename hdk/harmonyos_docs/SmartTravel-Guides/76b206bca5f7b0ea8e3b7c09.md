# Camera

#### Scenario

HiCar can discover the in-vehicle cameras, including the factory-installed and user-installed cameras. Leveraging the capabilities of these cameras, HiCar can provide more value-added services for users. Examples:

     * **In-vehicle video call/conference call** : Users can use their in-vehicle camera and large screen to make a video call/conference call while ensuring driving safety (for example, in parking mode).
     * **Driver monitoring** : The AI computing power of HUAWEI HiCar phones and real-time data reported by driver seat cameras can be used to monitor drivers in real time and intelligently alert drivers when necessary.
     * **Gesture recognition** : The AI computing power of Huawei HiCar phones and real-time data reported by driver seat cameras can be used to recognize drivers' gestures to control HiCar apps and services.
     * **Driving safety assistance** : The AI computing power of Huawei HiCar phones and real-time data reported by dashcams can be used to perform auxiliary detection on driving safety and intelligently alert users.

To use camera-based services in HiCar, implement camera-related APIs.

Implement the camera-related APIs based on the camera API header files provided by the HiCar SDK, and generate the **libdmsdpcamerahandler.so** file. When running, the HiCar SDK searches for the .so file. If the file is not found, it is considered that the Camera-related APIs have not been implemented. If the file is found, the SDK dynamically loads the .so library and obtains camera data from the head unit through the APIs implemented in the library. For details about the implementation process, please refer to **dmsdp_camera_sdk_samples.c** in the HiCar SDK package.

     1. During initialization, the HiCarSDK attempts to open the **libdmsdpcamerahandler.so** file. If the file can be opened, it is considered that the head unit has implemented the camera virtualization function. In this case, the HiCarSDK reports that the head unit has the virtual camera capability. If the file cannot be opened, the virtual camera capability will not be reported.
     2. One of the camera callbacks is a service status listener registered with the head unit. Cache the listener pointer in the HiCarController for reporting the camera status change (for example, busy or idle) or quantity change (for example, when a USB camera is inserted or removed).
     3. **GetCameraCapability** is called to query the camera capabilities of the head unit, including the number of cameras, and ID, supported resolution, frame rate, and data format of each camera. If the head unit has multiple cameras, it needs to determine which cameras are used for distributed virtualization based on the actual service requirements. While a camera may have multiple capabilities, only one supported capability needs to be reported. It is recommended that the H.264 or H.265 data type be returned. If the camera does not support the output of H.264/H.265 video streams, the NV21 or RGB565 format is also acceptable.
     4. The head unit needs to monitor the status change of the local camera. For example, the head unit needs to perform the following: (1) Detects that the camera is busy when it is enabled. (2) Queries the camera information when a USB camera that will be used for distributed virtualization is inserted. (3) Detects loss of a reported USB camera when it is removed.
     5. After receiving the camera status changes, the HiCar SDK updates the local cache information and reports the changes to the phone.
     6. Before the HiCar SDK opens the camera, it calls **RegisterSendDataCallback** to register the camera data callback handle and uses the handle to send back camera video stream data.
     7. The HiCar SDK calls **OpenCamera** to open the camera, carrying the camera parameters. After the camera is opened, the camera data is returned.
     8. During service running, the HiCar SDK may update the camera configuration, such as the camera frame rate. In this case, the **UpdateConfig** API must be called to deliver the new configuration. If the camera does not support configuration updates, keep the API unimplemented.
     9. The HiCar SDK calls **CloseCamera** to close the camera when it does not require the camera data, so as to release the locally cached resources, such as the camera data callback handle.

#### API Description

The camera APIs defined in the HiCar SDK abstract camera operations and encapsulate them into APIs for enabling, disabling, updating settings, querying capabilities, registering event listeners, and more. Implement the basic camera operations based on the API descriptions.
    
    **dmsdp_business.h** : defines result codes and status codes.
    **dmsdp_camera_data_type.h** : defines the camera data objects.
    **dmsdp_camera_handler.h** : defines the camera interfaces.

#### Development Procedure

     1. Sort out the camera hardware information of the head unit and determine the head unit cameras that need to be virtualized in distributed mode for the phone. Only the cameras that will be used in virtualization need to have their information collected and reported.
     2. The HiCar SDK needs to operate the camera of the head unit through the corresponding APIs. The implementation must include a mechanism to resolve possible conflicts between the SDK and other in-vehicle services in using the camera.
     3. After the head unit reports the camera capability to the phone, the camera status may change. For example, the camera is used by other services of the head unit, the camera service becomes unavailable after the USB camera is removed, or a different camera is inserted into the USB port. If the camera whose status changes needs to participate in the virtualization service, you need to monitor the status change of the corresponding camera.
     4. Implement the camera-related APIs based on the camera API header files, and provide the camera operating and status listening capabilities.
     5. Build the so.file and deploy it in the head unit system for testing.
