# Call State and Focus

#### Scenario

By default, the HiCar app provides the call service. If the head unit also provides the call service, conflicts may occur when they run at the same time. Therefore, the head unit should notify the HiCar app of the native call service state. When the HiCar app provides the call service, the head unit needs to report the call/hang-up event based on the call state of the HiCar app when the user presses the control button. Therefore, the head unit needs to obtain the call state from the HiCar app.

For details about the related data format, please refer to [Call State](https://developer.huawei.com/consumer/cn/doc/development/SmartTravel-References/call-focus-0000001153460174) in the **APIs Between the HiCar App and Head Unit** section in the API Reference.

If the head unit call conflicts with the HiCar call, the conflict will be resolved using solutions described in Table 1.

**Table 1** Call conflict scenarios  Conflict Scenario | Solution  
---|---  
There is an incoming call for the head unit during a HiCar call. | The mechanism is as follows:
     * If the incoming call for the head unit is a high-priority call, for example, an E-Call, the HiCar call will be released. 
     * If the incoming call for the head unit is a regular call, such as a B-Call, I-Call, or Bluetooth call, when the user answers the call, the HiCar call will be released. When the user declines the call, the HiCar call will not be affected.   
There is an outgoing call from the head unit during a HiCar call. | The HiCar call will be released.  
There is an incoming call for HiCar during a head unit call. | The mechanism is as follows:
     * If the outgoing call from the head unit is a high-priority call, for example, an E-Call, the HiCar call will be released. 
     * If the incoming call for HiCar is a regular call, such as a B-Call, I-Call, or Bluetooth call, the head unit will display the HiCar calling screen or floating window on the head unit screen. When the user answers the call, the head unit call will be released. When the user declines the call, the head unit call will not be affected.   
There is an outgoing call from HiCar during a head unit call. | The head unit call will be maintained or released.  
  
**Table 2** APIs for connecting and releasing HiCar calls  Header File | Method | Description  
---|---|---  
hicar.h | HiCarPostEvent | Sends a button event. When handling a call conflict scenario, the HMI app can reuse the button event to connect or release a call.
     * **KEYCODE_CALL** (value being **5**): The HiCar call is connected. 
     * **KEYCODE_ENDCALL** (value being **6**): The HiCar call is released.   
  
#### Development Procedure

     1. When a native call starts or ends, the head unit notifies HiCar of the call state through **HiCarSendData**.
        * This API notifies the HiCar app that the call service is unavailable when a native call is started. 
        * This API notifies the HiCar app that the call service is available when a native call ends. 

The head unit sends the following data: 
    
    {
        "isCallAvailable":true
    }

     2. The HiCar app notifies the head unit when the call state changes. The head unit can use the **DataReceive** method to determine the **dataType** and then obtain the call state. The head unit receives the following data:
            
            {
                "callState":1
            }

     3. For details about how to connect or release a HiCar call by sending a button event, see [Managing Buttons, Knobs, and Touchpads](https://developer.huawei.com/consumer/cn/doc/development/SmartTravel-Guides/physical-key-knob-0000000000105717).
