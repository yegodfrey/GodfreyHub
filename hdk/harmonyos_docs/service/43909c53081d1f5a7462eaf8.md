# HarmonyOS Skill开发规范

本文档说明了HarmonyOS Skill的完整格式规格定义。文档版本V6，最后修改时间为2026-05-20。

## 约束词说明

本规范及Skill正文统一使用以下中文约束词表达要求强度：

|约束词|对应 RFC 2119|含义|
|:------|:----------|:--------------------|
|**必须**|MUST|强制要求，不可违反|
|**禁止**|MUSTNOT|绝对禁止，不可违反|
|**应该**|SHOULD|强烈建议如此；若偏离须有充分理由并说明|
|**不应该**|SHOULD NOT|强烈不建议如此；若仍为之须有充分理由并说明|
|**可以**|MAY|可选，由实现方或读者自行判断|

在规范文档中，上述约束词约束**Skill开发者** ；在Skill正文（SKILL.md body）中，上述约束词约束**Agent运行时行为**。

## 目录结构

Skill是一个目录，**必须**包含SKILL.md和module.json两个文件：

```codeblock
skill-name/
├──Skill.md          # 必选：元数据 + 指令（面向 Agent）
├── module.json       # 必选：平台配置（面向运行时框架）
├── scripts/          # 可选：脚本文件（Agent可执行、读取或修改，由正文指令决定）
├── references/       # 可选：参考文档（Agent按需读取）
├── assets/           # 可选：静态资源（配合脚本和正文使用）
└── ...               # 其他文件
```

目录名**必须**与Skill.md frontmatter的name字段一致。

### SKILL.md格式

SKILL.md由YAMLfrontmatter + Markdown正文组成。

### 计量标准

本规范涉及三种长度单位：

|单位|定义|校验性质|适用场景|
|:--------|:--------------------------------------------------------------------------|:-------------------------------|:--------------------------------------|
|**字符**|Unicode字符计数------每个中文汉字、英文字母、数字、空格、标点均计为 1 个字符（等价于 len(text) / text.length）|硬校验（**必须**通过）|name、description、compatibility、toolName|
|**行**|以换行符分隔计数，空行计入|硬校验（总行数**必须** ）/ 建议（内容块行数**应该**）|正文总长、各内容块参考行数|
|**Token**|模型tokenizer将文本切分后的最小处理单元|软校验（**应该**通过）|description Token预算、正文Token预算|

> 说明
>
> 硬校验不通过则发布失败；软校验不通过**应该**修正------若偏离须有充分理由。

**为什么用字符做硬校验？**

* **跨模型一致**：同一文本在任何模型上字符数相同，但Token数因tokenizer不同可差2--3倍。
* **开发者友好**：标准字符串长度函数即可验证，无需安装tokenizer库。
* **业界对齐**：主流规范均以字符为硬限制------AgentSkills 开源规范 [R1]（≤ 1024 characters）、OpenAI Function Calling [R2]（≤ 1024 characters）

**为什么Token做软校验？**

字符硬校验存在盲区------"少行长文"或"高密度短文"可能在字符/行数内合规，但实际Token消耗远超设计预期。Token软校验作为补充约束，确保上下文成本可控。"软"体现在范围有弹性：不同模型 tokenizer效率不同，同一文本在不同模型上Token数天然有差异，因此以统一基线估算并以**应该**（SHOULD）约束。

**字符与Token的换算参考：**

|指标|DeepSeek V4|Qwen 3.6|GPT-5.5|Claude Opus 4|Gemini 3.1|
|:-------------|:----------|:---------|:------|:------------|:---------|
|1 中文字符 ≈ token|**0.6**|0.56--0.67|~0.7|0.6--0.75|~0.8|
|1 英文字符 ≈ token|**0.3**|0.25--0.33|~0.25|~0.25|~0.25|
|来源|[R3]|[R4]|[R6]|[R7]|[R8]|

> 说明
>
> DeepSeek V4、Qwen 3.6 数据来自官方文档；Claude Opus 4数据基于官方count_tokens API的大语料（现代中文 ≥ 5K 字符）实测；GPT-5.5、Gemini 3.1 数据基于官方tokenizer工具实测验证，可能存在微小误差，实际以模型返回的 usage 为准。
>
> 当代主流模型的中文tokenizer效率已普遍收敛至 0.6--0.8 token/字区间，模型间差异显著缩小。英文在各模型间差异更小（~0.25 token/字符）。

**规范基线系数** ：中文**0.6 token/字符** 、英文**0.3 token/字符**。此基线取自当代主流模型的效率下界，适用于Harmony OS的主要运行场景。规范中所有Token估算和软校验阈值均基于此系数计算。

**中英文分层限定的推导**：

中文信息密度约为英文的 2 倍------表达同等语义所需字符约为英文的一半。为使中英文description在相同Token预算下承载接近等量的语义，中文字符上限取英文的一半：

|语言|必须上限|× 基线系数|≈ Token|
|:-|:------|:-----|:-----------|
|中文|512 字符|× 0.6|≈ 307 tokens|
|英文|1024 字符|× 0.3|≈ 307 tokens|

Token成本等价，2 倍系数成立。此策略同时与业界 1024 字符上限（AgentSkills开源规范 [R1]）保持兼容------英文直接对齐，中文取半。

### Frontmatter

|字段|必选|含义|
|:------------|:-|:--------------------|
|name|是|Skill的唯一标识，与目录同名|
|description|是|Agent判断是否激活Skill的语义描述|
|license|否|许可证名称或引用|
|compatibility|否|环境要求说明|
|metadata|否|任意键值对，供扩展使用|
|allowed-tools|否|预批准可使用的工具，空格分隔|

> 说明
>
> 以上 6 个frontmatter字段与AgentSkills开源规范 [R1] 保持一致。

**最简示例：**

```codeblock
name: time-manager
description: >
  时间管理技能，处理闹钟、日程、计时器、秒表的增删改查。
  适用情形：用户要设闹钟、建日程、倒计时、用秒表，或提到"提醒""闹钟""日程"等关键词。
  不适用情形：待办事项、备忘录、定时任务。
```

**name字段**：Skill的唯一标识。

* 1--64 字符，仅 [a-z0-9-]
* 不以 - 开头/结尾，不含连续 --
* **必须**与父目录名一致
* **命名示例**：time-manager、phone-call、image-edit

**description字段**：Agent判断是否激活Skill的唯一语义来源。中英文采用不同字符上限以保持Token消耗均衡：

|语言|字符硬校验|Token 软校验|
|:-|:-------------------------------|:------------------|
|中文|**应该** ≤ 256 字符，**必须** ≤ 512 字符|**应该** ≤ 300 tokens|
|英文|**应该** ≤ 512 字符，**必须** ≤ 1024 字符|**应该** ≤ 300 tokens|

> 说明
>
> Token软校验阈值按基线系数计算（512 × 0.6 ≈ 307，1024 × 0.3 ≈ 307，统一取整 300）。description在渐进加载阶段为所有Skill常驻加载，长度直接影响元数据层的总Token消耗。保持精炼有助于支持更大规模的Skill并发常驻。

**必须**包含以下结构中的至少一项（能力概括或适用情形）：

1. **能力概括** （**应该**）：一句话核心身份 + 关键能力展开。用具体动词 + 明确对象，不使用泛化词
2. **适用情形** （**应该**）：正向触发条件。覆盖正式/口语/缩略三种表述，包含隐式触发场景
3. **不适用情形** （**可以**）：负向排除边界。只陈述事实，说明不处理的能力范围

**description约束：**

* **必须**只陈述事实边界，不做价值评价
* **禁止**使用比较级贬义（"比 xx 更好"）
* **禁止**使用泛化词（"智能助手"）或营销词（"最强"）
* **不应该**包含具体实现逻辑、调用流程或内部工具名称------description描述"做什么"，不描述"怎么做"

> 说明
>
> 触发关键词由构建工具在发布时自动从description中提取，开发者无需手写。**应该**确保适用情形覆盖同一意图的变体表达，以提升自动提取质量。

**license字段**

可选。许可证名称或对打包许可证文件的引用，建议保持简短。

**compatibility字段**

可选。描述Skill的环境要求，≤ 500 字符。仅在Skill有特定环境依赖时填写。

**metadata字段**

可选。字符串键值对，供扩展使用。此字段仅为兼容AgentSkills开源规范 [R1]，当前规范未做差异化定义。

**allowed-tools字段**

可选。预批准可使用的工具，空格分隔。Agent调用已预批准的工具时可直接执行，无需额外授权确认。
> 说明
>
> 此字段源自AgentSkills开源规范 [R1]，标记为Experimental，具体支持程度由Agent实现决定。

### 正文内容

frontmatter后面的Markdown正文是Skill的指令部分。

|校验维度|约束|性质|
|:----|:-------------------|:--|
|行数|**必须** ≤ 500 行|硬校验|
|Token|**应该** ≤ 5000 tokens|软校验|

超出行数限制的内容**必须**剥离到references/。
> 说明
>
> 500 行按典型行长换算约 3000--5000 tokens（基线系数：中文 0.6、英文 0.3）。5000 tokens软校验上限与AgentSkills开源规范 [R1] 的指令层推荐一致。行数硬校验与Token软校验配合，可防止"少行长文"或"多行空文"绕过单一维度的限制。精简的Skill正文不仅降低Token消耗，还能提升Agent执行准确率。

Skill正文只写**模型自身无法可靠完成的**部分，包括但不限于：

* **模型会做错的**：领域概念混淆、意图消歧规则、参数映射逻辑
* **模型做得不稳定的**：高频场景的推理模式、多步流程的执行顺序
* **做错了代价大的**：不可逆操作的确认机制、安全红线、数据风险约束
* **产品特定的体验要求**：输出格式、交互话术、降级策略

模型已能稳定处理的，**不应该**写入------无论是通用常识还是领域知识。冗余内容不仅浪费Token，还会干扰Agent决策。
> 说明
>
> Skill正文用四层结构回答Agent运行时的四个核心问题：**你知道什么** （领域知识）→ **你能做什么** （工具定义）→ **你该怎么做** （经验攻略 + 操作规程 + 安全红线）→ **你怎么协作**（与人协作）。每一层只写模型自身无法可靠完成的部分------冗余即是干扰。

正文按**知识层** → **能力层** → **编排层** → **协作层**四层组织，包含 6 个内容块：

|内容块|所属层|Skill开发遵从要求|Agent行为遵从要求|参考行数|
|:--------|:--|:-------------------------------|:-------------------------|:------|
|领域知识|知识层|**应该**写入领域特有概念|作为背景知识，辅助意图判断|10--25|
|工具定义|能力层|toolDependencies非空时**必须**写入且一一对应|作为可用能力清单，据此选择工具|50--150|
|经验攻略|编排层|**应该**覆盖高频场景|**应该**优先匹配，可灵活调整|30--60|
|操作规程（SOP）|编排层|涉及不可逆操作或多步依赖时**应该**写入|**必须**严格按序执行，禁止跳步|20--40|
|安全红线|编排层|**应该**列出领域特有禁止项|**禁止**违背，绝对底线|10--20|
|与人协作|协作层|存在歧义或缺参场景时**应该**写入|**应该** 按策略执行，高风险场景**必须**确认|15--30|

> 说明
>
> "参考行数"为编写指导（**应该**），不作为校验约束。

下面逐块说明。

**领域知识**

该领域的关键Note，**应该**控制在 3--5 条、每条 1--2 行，只写模型容易混淆或做错的要点。

知识量 < 10 行**应该** 直接写入正文。大段领域知识**可以** 剥离到references/，正文只放索引，引用**必须**保持一层深度，不嵌套。

```codeblock
## 领域知识
时间管理Skill覆盖闹钟、日程、计时器、秒表四类能力，用以支持不同时间粒度和提醒强度的场景。

关键 Note：
- 提醒我" ≠ 闹钟：需按优先级路由------秒/分钟级→计时器，"叫我/叫醒"→闹钟，高优先级事件→闹钟，低优先级→日程，兜底按 ≤24h→闹钟 / >24h→日程
- 取消 ≠ 删除：闹钟"取消/关闭"是关闭开关（保留在列表），"删除"是彻底移除不可恢复
- 周期闹钟 ≤ 24h：超出 24h 的周期走日程
- rangeType 语义映射：all=全部, latest=最近/下一个, newest=刚创建, current=上次操作的

扩展知识 → references/（可以，有大段知识时才拆）
- 时间表达式映射规则 → references/time_expression.md
```

**领域概念判别标准** ：存在用户心智与系统模型不一致的认知偏差时**应该**写入。

* 领域型Skill（相册/日历/联系人）**应该**写入
* 工具型Skill（手电筒/亮度/WiFi）**可以**省略
* 跨域型Skill（智能推荐/场景模式）涉及概念混淆时**应该** 写入，否则**可以**省略

**工具定义**

Skill的工具能力分为三类：

|类别|调用方式|Schema 进入 LLM 的位置|注册归属|
|:-------------|:-----------------------|:----------------------|:------------|
|系统预置工具|直接调用|tools[]（固定加载）|平台内置|
|Function与CLI工具|通过invoke / exec调用|system message（Skill正文）|平台注册 /Skill私有|
|脚本工具|通过exec调用ohos-arktsScript|system message（Skill正文）|Skill私有|

```codeblock
工具分类
│
├── 一、系统预置工具（直接调用）
│   exec / invoke / read / write / web_search / web_fetch / load_skill
│
├── 二、Function 与 CLI 工具（业务工具）
│   ├── Function 工具（通过 invoke 调用）
│   │   ├── 平台注册 ── Schema 由平台自动注入
│   │   └──Skill私有 ── Schema 由开发者手写
│   └── CLI 工具（通过 exec 调用）
│       ├── 平台注册 ── Schema 由平台自动注入
│       └──Skill私有 ── Schema 由开发者手写
│
└── 三、脚本工具（通过 exec ohos-arktsScript调用）
   Skill私有脚本（不支持平台管理）
```

**一、系统预置工具**

平台默认提供的基础执行能力，所有Skill可用。Agent在tools[]中直接看到并调用，无需经过invoke或exec中转。

|工具|说明|
|:-----------------------|:-----------|
|exec(command)|执行CLI命令或脚本|
|invoke(funcName, params)|调用Function工具|
|read / write|读取或写入文件与数据|
|web_search|网络搜索|
|web_fetch|获取指定URL的内容|
|load_skill|加载其他Skill|

> 说明
>
> 系统预置工具无需在toolDependencies中声明，平台默认加载。

**二、Function与CLI工具**

承载业务逻辑的工具，按调用通道分为Function工具和CLI工具，按注册归属分为平台注册和Skill私有。

**Function工具**（通过invoke调用）

适用于有结构化参数和返回值的业务函数。Agent通过invoke(funcName, params) 调用，平台执行引擎根据funcName路由到具体实现并做参数校验。

* **平台注册** ：工具在工具管理平台注册，Skill通过toolDependencies声明依赖，平台在Skill激活时自动将JSON Schema注入Skill正文。Skill开发者只需编写语义引导（约束、语义等），**不应该** 在正文中手写 Schema。工具尚未在平台注册或需要快速调试时，开发者**可以**在正文中手动写入Schema，待平台注册完成后移除手写部分，由平台自动注入。
* **Skill私有** ：不注册到平台，Skill开发者在正文中完整定义（Schema+ 语义）。**禁止**列入toolDependencies。

调用示例：invoke(funcName: "create_schedule", params: { title: "周会", startTime: "2025-01-15T09:00:00" })

**CLI 工具**（通过 exec 调用）

适用于命令行工具。Agent通过 exec(command) 调用，将命令、子命令和参数拼接为完整命令字符串。一个CLI程序为一个工具条目（包含该程序的所有子命令），以**命令表**描述可用命令------每行列出命令模板（含flag、位置参数占位符）、说明和调用样例。

* **平台注册** ：工具在工具管理平台注册（type: "cli"），Skill通过toolDependencies声明CLI程序名，平台在Skill激活时自动将命令表注入Skill正文。平台执行引擎对命令做安全校验。工具尚未在平台注册或需要快速调试时，开发者**可以**在正文中手动写入命令表。
* **Skill私有** ：不注册到平台，Skill开发者在正文中编写完整命令表。**禁止**列入toolDependencies。

调用示例：

```codeblock
exec(command: "ohos-aa start-a EntryAbility -b com.example.app -m entry")
```

**平台注册 vsSkill私有**：

|维度|平台注册|Skill私有|
|:---------------|:--------------------------|:--------------|
|Schema 来源|工具管理平台|Skill正文（开发者手写）|
|Schema 注入|平台自动注入（工具尚未注册或快速调试时也支持手动写入）|开发者手动写入，平台不自动注入|
|toolDependencies|**必须**声明|**禁止**声明|
|版本管理|平台统一管理，可独立于Skill升级|跟随Skill版本|

> 说明
>
> Skill开发者**应该**优先使用平台注册工具------Schema由平台维护，可跨Skill共享，版本和权限由平台统一治理。仅当工具为Skill专属逻辑、不适合注册到平台时，才使用Skill私有工具。

**三、脚本工具**

Skill私有的ArkTS / Python 等脚本文件，位于scripts/ 目录，不支持平台管理。统一通过exec调用ohos-arktsScript命令执行，参数包含 --skillName、--scriptPath、--functionName、--args。

Skill正文**应该** 为每个脚本说明用途、参数和交互方式（执行、读取或修改）。**禁止**列入toolDependencies。

调用示例：

```codeblock
exec(command: "ohos-arktsScript--skillName time-manager --scriptPath ./scripts/data_export.ETS--functionName exportSchedule --args '{\"format\":\"csv\",\"range\":\"2025-01\"}'")
```

工具条目按类型包含不同的必选字段：

|字段|Function工具|CLI工具|脚本工具|
|:----------|:--------------------|:-------------------------|:-------------------|
|toolName|**必须**。函数名|**必须**。CLI 程序名|---（用路径标识）|
|description|**必须**|**必须**|**必须**|
|参数|**必须**。JSON Schema或简写|---|**必须**|
|命令|---|**必须**。命令表（命令模板 + 说明 + 样例）|---|
|路径|---|---|**必须**|
|交互方式|---|---|**必须**（执行 / 读取 / 修改）|

> 说明
>
> **工具数量指导** ：单个Skill**应该**控制在 5--20 个工具。推导依据：每个工具Schema约 200 tokens，20 个即占 ~4000 tokens，叠加正文接近LLM有效工作区上限；工具数量过多通常意味着违反G3单一职责，应考虑拆分。
>
> **toolName格式约束**：1--64 字符，仅允许 [a-zA-Z0-9_-]，大小写敏感，与OpenAI、Anthropic、MCP (SEP-986) 标准兼容。不同类型的工具遵循各自的命名惯例：
>
> * **Function工具** ：**应该**使用 snake_case（如 create_schedule、delete_alarm），与主流LLM toolcalling生态一致
> * **CLI工具**：使用 CLI 程序的实际名称（如 ohos-aa），保持与系统命令一致
> * **系统预置工具**：简短动词命名（exec、invoke、read、write 等）

returns、约束、语义 等字段为可选，按需加入。其中 语义 用于承载JSON Schema无法表达的领域映射规则或SOP关联。

**经验攻略**

高频场景的Few-shot示例表，用于Agent模式识别。**应该** 提供 5--15 条；场景数量有限的Skill**可以** 少于 5 条。"要点"列标注**隐含推理** ，**不应该**重复调用链。

* 高频场景**应该**列明
* 场景空间较大时，**不应该**逐一枚举长尾场景

> 说明
>
> 高频场景**应该** 写入经验攻略，中频场景**应该** 由Agent通过工具+约束自由组合，长尾场景**应该**仅以安全红线约束。

```codeblock
## 经验攻略（Exemplar Playbook）

| 用户输入                  | 调用能力                          | 要点（隐含推理）                                     |
|--------------------------|----------------------------------|------------------------------------------------------|
| 明天早上7点叫我起床         | create_alarm(time, event)         | "叫我"语义→闹钟；"早上7点"→07:00                        |
| 下周三下午开会              | check_schedule → create_schedule   | 先查冲突再创建；缺时间点→默认 14:00（"下午开会"常识推断） |
| 提醒我3点买菜              | create_schedule(time, event)      | "3点"→15:00（买菜=白天活动）；"提醒"+低优先级→日程        |
| 帮我倒计时5分钟             | create_timer(duration)            | 有时长→计时器（非秒表）                                  |

```

**操作规程（SOP）**

关键操作的强制执行链路。**应该** 控制在 3--5 条，每条含检查门（确认门 / 过滤门 / 回滚窗口）。**必须**严格按序执行，不可跳步、不可变序。

判别标准：涉及数据变更、不可逆操作或多步依赖 → SOP；仅影响体验优劣 → 经验攻略。

```codeblock
## 操作规程（SOP）

以下链路必须严格按序执行，任何步骤不可跳过。

### SOP-1：批量删除日程/闹钟（rangeType=all）
用户说"都删了""全部删掉"
  ↓
rangeType 设为 all，禁填 entityId   ← [参数门] 必须，防止误删单条
  ↓
反述确认："将删除您所有的[类型]，确认吗？" ← [确认门] 必须，不可跳过
  ↓
执行 delete_schedule / delete_alarm

### SOP-2：创建日程冲突检测
用户要求创建日程
  ↓
check_schedule(time) 查询冲突        ← [检查门] 必须先查后建
  ↓ 有冲突
告知冲突 + 建议空闲时段 → 等用户确认  ← [确认门] 用户选择后再创建
  ↓ 无冲突
create_schedule(...)
```

**安全红线**

执行行为的禁止项清单。只写底线，**不应该**逐一枚举长尾场景。

```codeblock
## 安全红线

1. 用户时间表述有歧义时（"八九点""三四点"）禁止直接调用工具，必须先追问确认
2. rangeType=all时禁止填写 entityId，禁止继承上轮的具体 time/event/entityId
3. 回复中禁止包含系统内部字段（messageId、entityId、占位符标记等）
4. 禁止臆想凭空生成工具返回结果
5. 查询结果 > 3 条时禁止逐条列举，只输出"您共有[N]个[类型]"并引导查看卡片
```

**与人协作**

信息不全、歧义、失败、高风险场景下的协作策略。写入时**应该**覆盖四类：缺参询问、歧义消解、失败降级、高风险确认。

Skill开发者**应该**根据场景明确以下协作策略：

* **何时澄清**：哪些参数缺失时必须询问，哪些可用默认值跳过
* **澄清粒度**：单次澄清聚焦单个关键信息还是合并多个
* **澄清方式**：纯文本对话还是结合GUI选项

```codeblock
## 与人协作

| 场景                    | 策略                                          | 范例                                      |
|------------------------|----------------------------------------------|--------------------------------------------|
| 缺时间点（只给日期）      | 默认 9:00，不追问                              | "明天开会" → 默认明天 9:00                    |
| 模糊时段                 | 套用常识默认值                                  | "早上"→7:00、"中午"→11:00、"傍晚"→18:00       |
| 歧义时间（"八九点"）      | 必须追问，不可拆分为多个操作                  | "八九点提醒我" → "请问是8点还是9点？"           |
| 上午/下午歧义             | 结合事件常识推断                                | "3点买菜"→15:00、"7点起床"→07:00               |
| 批量删除                 | 必须反述确认                                | "将删除您所有闹钟，确认吗？"                    |

```

## **module.json 格式**

> 说明
>
> 平台侧配置文件，面向构建系统与运行时框架。字段命名遵循camelCase，与Harmony module.json5 保持一致。

|字段|类型|必选|说明|
|:-----------------|:-------|:-----------------|:---------------------------------------------------------------------------------------------|
|version|string|是|Skill版本号，**必须**遵循语义化版本（Semver）格式：主版本号.次版本号.补丁号（如 1.0.0）|
|availableOn|string[]|否（系统自动填充）|Skill可被哪些Agent发现和使用，详见availableOn字段说明|
|toolDependencies|string[]|否（不填时缺省为空）|本Skill依赖的平台注册工具列表。**必须**与工具管理平台中的注册工具对齐|
|abilityName|string|否|ETS脚本运行关联的 Ability，仅UIAbility或type=service的ServiceExtension，不填时默认入口Ability；无ETS脚本的Skill不用配置该字段|
|visibility|string|否（不填时缺省为 "system"）|Skill可见性：private（仅本应用可见）/ system（系统应用可见）/ public（所有应用可见）。不填时默认 "system"|
|srcEntries|string[]|否（不填时缺省为空）|ETS脚本文件路径，端侧框架编译为ABC存入HAP。数组大小0--100，仅Skill-name/scripts/ 目录下|
|permissions|string[]|否（不填时缺省为空）|调用Skill所需权限。仅对系统Skill生效|
|requestPermissions|string[]|否（不填时缺省为空）|ETS脚本运行时所需系统权限|
|minAPIVersion|integer|否（自动生成）|ETS脚本运行的最小SDK API版本。编译构建时自动生成，对应build-profile.json5的compatibleSdkVersion|
|targetAPIVersion|integer|否（自动生成）|ETS脚本运行的API目标版本。编译构建时自动生成，对应build-profile.json5的targetSdkVersion。**必须** ≥ minAPIVersion|

**基本示例**：

```codeblock
{
  "version": "1.0.0",
  "availableOn": ["phone", "cloud"],
  "toolDependencies": [
    "create_schedule",
    "check_schedule",
    "delete_schedule",
    "create_alarm"
  ]
}
```

> 说明
>
> availableOn由系统自动填充，开发者也可手动声明。toolDependencies仅列出平台注册的业务工具，须与SKILL.md工具定义一一对应。

**按需扩展**（有权限和版本要求时）：

```codeblock
{
  "version": "1.0.0",
  "availableOn": ["phone", "pc", "cloudSandbox"],
  "toolDependencies": ["create_schedule", "check_schedule"],
  "requestPermissions": [
    "ohos.permission.READ_CALENDAR",
    "ohos.permission.WRITE_CALENDAR"
  ],
  "minAPIVersion": 12,
  "targetAPIVersion": 13
}
```

**包含 CLI 工具时**：

```codeblock
{
  "version": "1.0.0",
  "availableOn": ["localSandbox"],
  "toolDependencies": [
    "ohos-aa",
    "create_schedule",
    "check_schedule"
  ]
}
```

> 说明
>
> 系统预置工具（exec、invoke、read、write 等）为平台默认加载，**不应该**在toolDependencies中声明。

### **version 字段**

Skill的版本号，**必须**遵循语义化版本（Semver [R9]）格式：主版本号.次版本号.补丁号。

* 主版本号：不兼容的Skill接口变更（如toolDependencies增删、description语义变更）
* 次版本号：向后兼容的功能新增（如新增经验攻略、补充领域知识）
* 补丁号：向后兼容的问题修复（如修正SOP描述、修复示例错误）

示例："1.0.0"、"2.1.3"

### **availableOn 字段**

声明Skill可被哪些Agent发现和使用。每个枚举值对应一个Agent运行位置，不在列表中的Agent无法看到该Skill。**由系统自动填充**，开发者也可手动声明。

|值|含义|
|:-----------|:---------------------|
|phone|手机|
|tablet|平板|
|pc|PC|
|wearable|可穿戴设备|
|car|车机|
|tv|智慧屏 / 电视|
|cloud|云端环境|
|cloudSandbox|云端沙箱环境（支持文件操作等需隔离的场景）|
|localSandbox|本地沙箱环境（PC / Linux本地容器）|

> 说明
>
> 设备枚举与Harmony module.json5的[deviceTypes](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/module-configuration-file)标签对齐；cloud、cloudSandbox、localSandbox为Skill规范扩展。

Skill**不应该**假设单机执行------HarmonyOS支持分布式超级终端，Skill可能被跨设备/跨环境调度。

### **toolDependencies 字段**

本Skill依赖的**平台注册工具**列表。缺省为空。

* 列出的每个工具名**必须**在工具管理平台中存在
* 列出的每个工具名**必须**在Skill.md ## 工具定义 中有对应条目
* 仅声明**平台注册**的Function工具和CLI工具（如 create_schedule、ohos-aa）
* 系统预置工具（exec、invoke、read、write、web_search、web_fetch、load_skill）为平台默认加载，**不应该**声明
* Skill私有工具（私有 Function、私有CLI、脚本）不在平台注册，**禁止**声明

运行时据此做：

* **依赖校验**：Skill安装/启用时检查工具管理平台中工具是否存在
* **权限推导**：从工具管理平台查每个工具的权限要求，与 requestPermissions 交叉校验
* **Schema 注入**：从工具管理平台拉取工具 JSON Schema，注入Skill正文（system message）
* **版本兼容**：结合minAPIVersion检测工具可用性
* **影响分析**：工具管理平台中工具升级/下线时反查受影响的Skill

### **abilityName 字段**

可选。ETS脚本运行关联的Ability名称，不填时默认入口Ability。无ETS脚本的Skill不用配置该字段。

* 只能配置当前module下的UIAbility（abilities标签下）或type=service的ServiceExtension（extensionAbilities标签下）
* 与其他module共用时**必须**确保Ability已注册

### **visibility 字段**

可选。控制在Harmony设备上哪些应用可以发现和调用该Skill，不填时默认 "system"。此字段仅在设备端（手机、平板等有 APP 生态的设备）有意义，云端环境不涉及应用级访问控制。

|值|含义|适用场景|
|:------|:----------|:------------------|
|private|仅本应用内可见|应用内部Skill|
|system|系统应用可见（默认）|系统预装Skill、开放平台Skill|
|public|对外公开，所有应用可见|系统预装Skill、开放平台Skill|

> 说明
>
> visibility 控制**应用级** 访问权限（同一设备上哪些 APP 可调用），availableOn 控制**设备/环境级**可见性（哪些Agent可发现该Skill），两者独立生效。

### **srcEntries 字段**

可选。Skill的ETS文件路径列表，有端侧脚本时填写。

* 数组大小**必须**在 0--100 之间
* 路径**必须**在Skill-name/scripts/ 目录下
* 端侧框架编译为ABC存入HAP

### **permissions 字段**

可选。调用本Skill所需的权限，有访问控制需求时填写。

* Schema与 abilities 标签下的 permissions 一致，只允许配置系统定义的权限
* 仅对系统Skill生效
* 不建议复用已有权限定义，建议新增权限来管控Skill的调用

### **requestPermissions 字段**

可选。ETS脚本运行时所需的系统权限，涉及敏感能力时填写。非ETS脚本的工具权限由工具管理平台中工具自身的权限声明承载。

### **minAPIVersion / targetAPIVersion 字段**

ETS脚本运行的 SDK API 版本约束。这两个字段在Skill编译构建时自动生成，开发者无需手动配置。

* minAPIVersion对应工程级 build-profile.json5 [R10] 中的compatibleSdkVersion
* targetAPIVersion 对应 build-profile.json5 中的targetSdkVersion；若未配置，则由compileSdkVersion自动生成
* targetAPIVersion **必须** ≥ minAPIVersion
* 相关标签与应用兼容性关系参见应用兼容性说明 [R11]

## **可选目录**

**scripts/**

脚本文件，Agent的交互方式由Skill正文指令决定：

* **执行**：Agent调用脚本并获取返回结果
* **读取**：Agent读取脚本内容以理解逻辑或辅助决策
* **修改**：Agent根据用户需求调整或生成脚本

脚本**应该**自包含或清晰声明依赖，包含有用的错误消息。

以下为常见脚本类型，平台不对脚本语言做封闭枚举。HarmonyOS在开源常见语言基础上扩展了ArkTS，实际支持情况取决于目标运行环境：

|脚本类型|后缀|适用场景|
|:------|:---|:----------------------------------|
|ArkTS|.ets|调用HarmonyOS底层API与UIAbility，系统调用深度最高|
|Shell|.sh|系统维护、文件批处理，全场景通用|
|Python|.py|数据处理、科学计算、AI推理|
|Node.js|.js|JSON 处理、Web工具链、API集成|

Python / Node.js 在终端设备不具备运行时，通过 subAgent子任务委托到PC或云侧执行，结果回传。subAgent为平台提供的子任务委托机制：当终端不具备某类运行时，Agent可将对应执行任务委托到具备运行时的设备或云侧完成，并将结果回传。

所有脚本**必须**在沙箱内运行：

|执行环境|沙箱机制|
|:-------|:-----------------------|
|终端ArkTS|HAP签名 + 系统权限模型|
|终端 Shell|受限 Shell沙箱|
|PC本地|OS级进程隔离|
|云 / 容器|容器沙箱（隔离文件系统 + 网络 + 资源配额）|

**references/**

Agent按需读取的参考文档。保持单个文件聚焦，引用一层深度，不嵌套。Agent未读取时零Token消耗。

**assets/**

静态资源：模板、图标、数据文件等，配合脚本和正文使用。

## **渐进加载**

Agent分级加载Skill，按需拉入更多细节：

|加载级别|内容|量级（软校验阈值）|时机|
|:-------------|:-------------------------------|:---------------------|:-----------------|
|**元数据**|name + description|≤ 300 tokens / 每个Skill|启动时为所有Skill加载|
|**指令**|SKILL.md 完整正文|≤ 5000 tokens|Skill被激活时加载|
|**ToolSchema**|运行时决定注入的工具的 JSON Schema|~200 tokens / 个|Skill被激活时注入tools[]|
|**资源**|scripts/ / references/ / assets/|按需|任务执行中按需加载|

> 说明
>
> 量级基于规范基线系数（中文 0.6、英文 0.3 token/字符）估算。实际Token消耗因模型 tokenizer 而异。

## **校验**

```codeblock
skills-ref validate ./my-skill
```

遵循本规范的Skill**必须** 通过硬校验（JSON Schema + lint），**应该**通过软校验（Token 预算）。

### **硬校验**

校验项包括：

* SKILL.md frontmatter 的 name 与目录名**必须**一致
* description **必须**不超过字符上限（中文 512 字符 / 英文 1024 字符）
* module.json 的 version **必须**符合 Semver 格式
* module.json 的 availableOn（如存在）每个值**必须**为合法枚举值（phone / tablet/ pc / wearable / car / tv / cloud / cloudSandbox / localSandbox）
* module.json 的 toolDependencies 中每个工具名**必须** 在Skill.md ## 工具定义 中有对应条目；Skill私有工具**禁止**出现在 toolDependencies 中
* targetAPIVersion 填写时**必须** ≥ minAPIVersion
* srcEntries 数组大小**必须**在 0--100 之间
* toolName **必须**匹配 [a-zA-Z0-9_-]{1,64}

### **软校验（Token 预算）**

遵循本规范的Skill**应该** 通过Token软校验。软校验基于规范基线系数（中文 0.6、英文 0.3 token/字符）计算，不通过时**应该**修正。

|校验项|阈值|推导|
|:----------------|:-------------------|:-----------------------------|
|descriptionToken量|**应该** ≤ 300 tokens|512 × 0.6 ≈ 307，取整 300|
|正文Token量|**应该** ≤ 5000 tokens|与AgentSkills 开源规范 [R1] 指令层推荐对齐|

校验工具内置参考 tokenizer（基于规范基线系数），无需在线 API。

```codeblock
# 校验输出示例
skills-ref validate ./my-skill

# ✅ PASS [硬校验]: description 480 chars (≤ 512)
# ⚠️ FAIl[软校验]: description ~320 tokens (> 300), 应该精简以控制常驻Token消耗
# ✅ PASS [硬校验]: body 380 lines (≤ 500)
# ✅ PASS [软校验]: body ~3200 tokens (≤ 5000)
```

### **安全检测**

遵循本规范的Skill在发布前**应该**通过安全检测。安全检测分为两个层次：

**静态规则扫描**

**必须**通过。基于正则匹配和模式识别的自动化扫描：

|检测项|约束|示例|
|:----|:-----------------------------------------|:---------------------------------|
|危险命令|scripts/ 中**禁止**包含高危命令|rm -rf /、chmod 777、curl| bash、eval|
|硬编码凭据|正文和脚本中**禁止**包含硬编码的密钥、token或密码|api_key = "sk-xxx"|
|路径越界|脚本文件路径**禁止**包含目录穿越|../../etc/passwd|
|权限一致性|requestPermissions声明的权限**必须**与实际工具调用所需权限匹配|---|

**LLM 语义审计**

**应该**通过。基于大模型语义理解的内容审查：

|检测项|约束|
|:--------------|:------------------------------------------|
|PromptInjection|正文**禁止**包含试图覆盖Agent系统指令的内容|
|虚假声明|description **禁止**包含误导Agent激活决策的能力声明|
|声明一致性|description 中声明的能力**应该**在正文的工具定义或经验攻略中有对应支撑|
|权限提升|正文**禁止**诱导Agent绕过权限检查执行操作|

## **附录 A：设计原则速查**

**通用原则（G1--G9）**

|#|原则|一句话|
|:-|:----------|:----------------------------------------|
|G1|精确自描述|description 如实描述"做什么/不做什么"|
|G2|中立共存|不贬低、不夸大、不挤兑其他Skill|
|G3|单一职责|一个Skill只解决一个领域问题|
|G4|渐进披露|元数据→指令→资源分级加载|
|G5|最小声明|权限/工具/依赖按实际需要声明，不多不少|
|G6|可组合|输入输出可序列化|
|G7|模型能力互补|Skill只写模型自身无法可靠完成的部分，包括知识、流程、约束和体验要求|
|G8|能力与Skill解耦|平台注册工具由平台统一治理，Skill通过 toolDependencies 引用|
|G9|Agent自主规划优先|能由Agent动态组合的场景不固化为 SOP|
