# 架构设计

多设备场景的技术架构可在单设备应用架构的基础上叠加，开发者需要重点关注多设备可复用和产品特有特性的代码管理。为便于模块管理和清晰查看模块间的依赖关系，推荐采用 common、features、products三层工程结构。

图4-1 多设备应用开发模型

![](https://media:201786607381547925 "点击放大")

* common（公共能力层）：存放公共基础能力，包括通用的UI组件、数据管理等。多个feature间共用的能力都可下沉到common层。common层可编译成一个或多个HAR 包或 HSP 包，仅供 products 和 features 中的模块依赖，不可以反向依赖特性和产品层。
* features（基础特性层）：存放基础特性模块，每个 feature 包含其相关的 UI 及其业务逻辑，具备高内聚、低耦合和可定制的特点。无需单独部署的 feature 通常编译为 HAR 包或 HSP 包，供各个 product 的 Entry HAP 使用。需要单独部署的 feature 通常编译为 Feature 类型的 HAP 包，和 products 下 Entry 类型的 HAP 包进行组合部署。features 层可以横向调用及依赖 common 层，不可以反向依赖 products 层。
* product（产品定制层）：不同设备形态的 product 按需集成了本设备所需的特性，并进行产品化的定制。各个 product 各自编译为一个 Entry 类型的 HAP 包，作为应用的主入口。product 层向下依赖 features 层和 common 层，各 product 间不可相互依赖。default 类型的 product 是多个类型的设备公用的，如应用的部分界面在手机和平板上的 UX 设计相似，可共用 default。其 HAP包需同时配置 phone 和 tablet 设备类型。

下面是使用三层工程结构的具体工程示例：

```
/application 
 ├── common                  # 公共能力目录 
 │   ├── utils               # 工具类目录：如网络、图片、文件管理工具等  
 │   ├── components         # 公共组件目录：如共用的弹窗、列表、详情页组件等 
 │   └── ...                  
 │ 
 ├── features                # 基础特性目录 
 │   ├── login               # 登录模块 
 │   ├── setting             # 设置模块 
 │   └── ...                  
 │ 
 └── product                 # 产品定制目录 
     ├── phone               # 手机版本目录 
     ├── tablet              # 平板版本目录 
     ├── pc                   # PC版本目录 
     ├── default             # 默认设备泛类目录 
     └── ...
```
