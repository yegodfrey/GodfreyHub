# 代码开发

**一、概览**

![](https://contentcenter-vali-drcn.dbankcdn.cn/pvt_2/DeveloperAlliance_scene_100_1/3e/v3/-gGJLFc4SiOLvaoAYU28Cg/zh-cn_image_0000002656449270.png?HW-CC-KV=V1&HW-CC-Date=20260909T170923Z&HW-CC-Expire=31536000000&HW-CC-Sign=EB4A57EA4F3A5BB84C442F72017943747F96DAD8E4DFF0C50555CD32B39DBF16 "点击放大")

软件开发本质是一个在多维约束下使解空间逐层收敛的确定性工程，而LLM是具有随机性的概率预测器。 人类开发者依赖经验与记忆隐式完成这一收敛过程，LLM则擅长局部模式匹配但缺乏全局把控。因此，必须构建显性的双层约束体系来弥合这一鸿沟：

* 内部约束（Prompt）：约束推理轨迹，强制 LLM 将关键决策与设计思路显性化，降低生成的随机性。
* 外部约束（Harness）：构建开发闭环，以机械、语义等维度的校验结果作为反馈，驱动多轮定向修复。

本环节基于输入的需求描述文档（Spec文档），进行逻辑代码生成，并自动完成编译构建修复，代码检视修复，提交远程仓库等动作。主要任务如下：

**1）逻辑代码开发**

设计阶段：不是把需求改写成更长的说明，而是获取任务所需上下文做约束求解，先用需求内容确定任务方向和验收条件，再用项目搜索限定修改影响范围，用平台限制确定方案可行性，最终确定的方案通过Plan合同显性传递。

编码阶段：只在合同范围内做最小改动，不重新理解需求、只做有限的合同验证，避免自由发挥。

**2）编译构建+修复**

在逻辑代码开发环节结束后，对当前工程进行编译构建，如果构建的输出结果中包含错误信息，则基于此错误信息自动进行代码修复，修复后触发重新构建，直至问题修复完成。

**3）代码检视+修复**

针对编译成功的代码需要进一步进行功能实现层面的代码检视，在此环节，智能体会获取到此次需求开发影响的代码片段全集，并基于Spec文档中的场景描述进行"实现一致性"校验，对于一致性校验未通过的场景，则进入缺陷修复阶段，修复完成后重新进行全量的代码检视，直到全部场景检视通过。

**二、技术方案**

![](https://contentcenter-vali-drcn.dbankcdn.cn/pvt_2/DeveloperAlliance_scene_100_1/9b/v3/UREke0OUT2S0IAqfDmJryg/zh-cn_image_0000002686528877.png?HW-CC-KV=V1&HW-CC-Date=20260909T170923Z&HW-CC-Expire=31536000000&HW-CC-Sign=8B54DDF75CF8884BC17D05D81223D32407238418A70C4BD6B56F3BCEFC554A57 "点击放大")每个独立功能节点使用Subagent上下文隔离，外部Pipeline统一调度多任务，避免真正任务执行的Agent上下文累积进入低效区间，导致效率下降。

**编译构建及修复**

编译修复智能体基于用户预先的环境信息配置或自动在用户环境中定位到鸿蒙工具链的位置，通过调用编译工具对当前项目进行编译构建，如果编译构建输出结果中包含错误，智能体会自动展开修复，首先在常见的错误模式库中进行匹配，匹配到的问题则将对应修复经验作为知识输入给模型，最终完成修复，修复完成后则触发重新构建，验证修复效果。

**基于程序分析的代码检视及修复**

针对spec文档中描述的各个场景进行代码白盒层面的质量分析，基于ArkAnalyzer程序分析工具可以有效的实现对鸿蒙代码的数据流以及控制流分析，检视修复智能体以当前commit作为入口，对git diff进行解析，获取基本的代码片段以及文件信息，然后运行程序分析工具，输出包含完整代码段（类，函数等）的代码上下文，输入给模型进行场景功能实现一致性的判定。对于与代码实现不一致的场景，智能体会进行原始安卓应用代码的实现逻辑检测，与鸿蒙项目的实现逻辑进行对比，识别缺陷位置，最终自动完成修复，修复后则重新触发检视，验证修复后的效果。
