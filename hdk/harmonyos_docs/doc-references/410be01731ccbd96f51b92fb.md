#### [h2]lock

public void lock​()

Acquires the write lock. 

Acquires the write lock if neither the read nor write lock are held by another thread and returns immediately, setting the write lock hold count to one. 

If the current thread already holds the write lock then the hold count is incremented by one and the method returns immediately. 

If the lock is held by another thread then the current thread becomes disabled for thread scheduling purposes and lies dormant until the write lock has been acquired, at which time the write lock hold count is set to one.

If the lock is held by another thread then the current thread becomes disabled for thread scheduling purposes and lies dormant until one of two things happens:

#### [h2]tryLock

public boolean tryLock​()

Acquires the write lock only if it is not held by another thread at the time of invocation. 

Acquires the write lock if neither the read nor write lock are held by another thread and returns immediately with the value true, setting the write lock hold count to one. Even when this lock has been set to use a fair ordering policy, a call to tryLock() will immediately acquire the lock if it is available, whether or not other threads are currently waiting for the write lock. This "barging" behavior can be useful in certain circumstances, even though it breaks fairness. If you want to honor the fairness setting for this lock, then use [tryLock(0, TimeUnit.SECONDS) ](https://developer.harmonyos.com/cn/docs/documentation/doc-references/reentrantreadwritelock_writelock-0000001054678624#ZH-CN_TOPIC_0000001054678624__tryLock-long-java_util_concurrent_TimeUnit-) which is almost equivalent (it also detects interruption). 

If the current thread already holds this lock then the hold count is incremented by one and the method returns true. 

If the lock is held by another thread then this method will return immediately with the value false.

**Specified by:**

[tryLock](https://developer.harmonyos.com/cn/docs/documentation/doc-references/lock-0000001054678622#ZH-CN_TOPIC_0000001054678622__tryLock--) in interface [Lock](https://developer.harmonyos.com/cn/docs/documentation/doc-references/lock-0000001054678622)

**Returns:**

#### [h2]tryLock

public boolean tryLock​(long timeout, [TimeUnit](https://developer.harmonyos.com/cn/docs/documentation/doc-references/timeunit-0000001054838570) unit) throws [InterruptedException](https://developer.harmonyos.com/cn/docs/documentation/doc-references/interruptedexception-0000001054678421)

Acquires the write lock if it is not held by another thread within the given waiting time and the current thread has not been [Thread#interrupt](https://developer.harmonyos.com/cn/docs/documentation/doc-references/thread-0000001054238447#ZH-CN_TOPIC_0000001054238447__interrupt--). 

Acquires the write lock if neither the read nor write lock are held by another thread and returns immediately with the value true, setting the write lock hold count to one. If this lock has been set to use a fair ordering policy then an available lock will not be acquired if any other threads are waiting for the write lock. This is in contrast to the [tryLock()](https://developer.harmonyos.com/cn/docs/documentation/doc-references/reentrantreadwritelock_writelock-0000001054678624#ZH-CN_TOPIC_0000001054678624__tryLock--) method. If you want a timed tryLock that does permit barging on a fair lock then combine the timed and un-timed forms together: 
    
    if (lock.tryLock() ||
         lock.tryLock(timeout, unit)) {
       ...
     }

If the current thread already holds this lock then the hold count is incremented by one and the method returns true. 

If the lock is held by another thread then the current thread becomes disabled for thread scheduling purposes and lies dormant until one of three things happens: 

    * The write lock is acquired by the current thread; or 
    * Some other thread [Thread#interrupt](https://developer.harmonyos.com/cn/docs/documentation/doc-references/thread-0000001054238447#ZH-CN_TOPIC_0000001054238447__interrupt--) the current thread; or 
    * The specified waiting time elapses 

If the write lock is acquired then the value true is returned and the write lock hold count is set to one. 

If the current thread: 

    * has its interrupted status set on entry to this method; or 
    * is [Thread#interrupt](https://developer.harmonyos.com/cn/docs/documentation/doc-references/thread-0000001054238447#ZH-CN_TOPIC_0000001054238447__interrupt--) while acquiring the write lock, 
then [InterruptedException](https://developer.harmonyos.com/cn/docs/documentation/doc-references/interruptedexception-0000001054678421) is thrown and the current thread's interrupted status is cleared. 

If the specified waiting time elapses then the value false is returned. If the time is less than or equal to zero, the method will not wait at all. 

In this implementation, as this method is an explicit interruption point, preference is given to responding to the interrupt over normal or reentrant acquisition of the lock, and over reporting the elapse of the waiting time.

#### [h2]unlock

public void unlock​()

Attempts to release this lock. 

If the current thread is the holder of this lock then the hold count is decremented. If the hold count is now zero then the lock is released. If the current thread is not the holder of this lock then [IllegalMonitorStateException](https://developer.harmonyos.com/cn/docs/documentation/doc-references/illegalmonitorstateexception-0000001054518464) is thrown.

The returned [Condition](https://developer.harmonyos.com/cn/docs/documentation/doc-references/condition-0000001054518634) instance supports the same usages as do the [Object](https://developer.harmonyos.com/cn/docs/documentation/doc-references/object-0000001054678446) monitor methods ([Object#wait()](https://developer.harmonyos.com/cn/docs/documentation/doc-references/object-0000001054678446#ZH-CN_TOPIC_0000001054678446__wait--), [Object#notify](https://developer.harmonyos.com/cn/docs/documentation/doc-references/object-0000001054678446#ZH-CN_TOPIC_0000001054678446__notify--), and [Object#notifyAll](https://developer.harmonyos.com/cn/docs/documentation/doc-references/object-0000001054678446#ZH-CN_TOPIC_0000001054678446__notifyAll--)) when used with the built-in monitor lock. 

    * If this write lock is not held when any [Condition](https://developer.harmonyos.com/cn/docs/documentation/doc-references/condition-0000001054518634) method is called then an [IllegalMonitorStateException](https://developer.harmonyos.com/cn/docs/documentation/doc-references/illegalmonitorstateexception-0000001054518464) is thrown. (Read locks are held independently of write locks, so are not checked or affected. However it is essentially always an error to invoke a condition waiting method when the current thread has also acquired read locks, since other threads that could unblock it will not be able to acquire the write lock.) 
    * When the condition [Condition#await()](https://developer.harmonyos.com/cn/docs/documentation/doc-references/condition-0000001054518634#ZH-CN_TOPIC_0000001054518634__await--) methods are called the write lock is released and, before they return, the write lock is reacquired and the lock hold count restored to what it was when the method was called. 
    * If a thread is [Thread#interrupt](https://developer.harmonyos.com/cn/docs/documentation/doc-references/thread-0000001054238447#ZH-CN_TOPIC_0000001054238447__interrupt--) while waiting then the wait will terminate, an [InterruptedException](https://developer.harmonyos.com/cn/docs/documentation/doc-references/interruptedexception-0000001054678421) will be thrown, and the thread's interrupted status will be cleared. 
    * Waiting threads are signalled in FIFO order. 
    * The ordering of lock reacquisition for threads returning from waiting methods is the same as for threads initially acquiring the lock, which is in the default case not specified, but for fair locks favors those threads that have been waiting the longest.
